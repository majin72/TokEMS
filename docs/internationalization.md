# TokEMS 国际化规划

## 目标

TokEMS 面向全球大会运营团队。国际化会先覆盖管理后台的简体中文和英语，再扩展大会前台、通知模板、区域格式与集成适配器。

首批语言：

- `zh-CN`：默认语言，也是当前界面的基准语言。
- `en-US`：首个完整外语版本。

首版国际化工作聚焦界面、格式和错误信息。主办方填写的大会名称、议程、嘉宾介绍等业务内容仍由主办方维护，系统不会自动翻译。

## 当前状态

`v0.1.0` 的运行时文案主要直接写在 Vue、NestJS 和 Worker 源码中。日期和金额格式大多固定为 `zh-CN` 与 `CNY`，手机号、短信和支付流程优先支持中国大陆场景。

用户资料已经预留 `preferences.locale`，可以作为语言偏好的起点。当前还没有统一的翻译目录、语言切换器、缺失键检查和翻译覆盖率门禁。

## 实现原则

1. 语言代码使用 BCP 47，例如 `zh-CN`、`en-US`。
2. 界面语言、时区、货币和区域集成分别配置，避免把语言与业务地区绑定。
3. API 返回稳定的错误代码和参数，前端负责显示本地化文案。
4. 通知模板在发送时确定语言，并保留最终渲染内容用于审计。
5. 翻译键按产品域命名，拒绝用完整中文句子作为键。
6. 插值、复数和日期格式使用结构化参数，避免拼接句子。
7. 缺失翻译在开发和 CI 中报错，生产环境回退到 `zh-CN` 并记录可观测事件。

## 管理后台方案

管理后台采用 Vue I18n，使用 Composition API 与 TypeScript。翻译目录按语言和产品域拆分：

```text
apps/admin/src/i18n/
  index.ts
  locale.ts
  messages/
    zh-CN/
      common.ts
      auth.ts
      events.ts
      registrations.ts
      orders.ts
      invoices.ts
      templates.ts
      settings.ts
      audit.ts
    en-US/
      common.ts
      auth.ts
      events.ts
      registrations.ts
      orders.ts
      invoices.ts
      templates.ts
      settings.ts
      audit.ts
```

`zh-CN` 目录定义键结构，`en-US` 必须满足同一 TypeScript 类型。组件只调用翻译键和格式化函数，例如：

```ts
t('registrations.status.confirmed');
d(registration.createdAt, 'dateTimeShort');
n(order.amount / 100, { style: 'currency', currency: order.currency });
```

### 语言解析顺序

登录后：

1. 用户资料中的 `preferences.locale`。
2. 组织设置中的默认语言。
3. 浏览器支持的语言。
4. `zh-CN`。

登录前使用浏览器语言和本地缓存。用户在后台切换语言后，界面立即更新，并将偏好写回用户资料。组织管理员可以设置新成员的默认语言。

### 需要覆盖的界面元素

- 路由标题、导航、面包屑和空状态。
- 按钮、表单标签、占位符、校验提示和确认对话框。
- 表格列名、筛选器、分页、状态标签和批量操作。
- Toast、错误页、权限提示和审计动作名称。
- 日期、时间、数字、金额、百分比、时区和文件大小。
- 动态配置表单、模板编辑器和系统设置说明。

## API 与 Worker

API 对可预期业务错误返回稳定字段：

```json
{
  "type": "https://tokems.dev/problems/ticket-sold-out",
  "title": "Ticket inventory is unavailable",
  "status": 409,
  "code": "ticket.sold_out",
  "params": {
    "ticketTypeId": "..."
  }
}
```

后台使用 `code` 和 `params` 映射本地化文案。`title` 作为日志与未知客户端的安全回退，不承载需要逐字匹配的业务逻辑。问题详情结构遵循 [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)。

Worker 处理通知时保存以下信息：

- 模板键与模板版本。
- 目标语言和时区。
- 插值参数。
- 最终主题与正文。
- 提供商、发送结果和重试记录。

短信、邮件和站内通知分别维护文案，避免从长文本机械截断生成短消息。

## 大会前台与业务内容

后台稳定后，大会前台接入同一套语言规范。每场大会可以配置支持语言和默认语言，URL 采用明确的区域段，例如 `/en-US/events/...`。

需要增加本地化内容的数据对象包括：

- 大会名称、短名称、简介和 SEO 字段。
- 议程标题、摘要和会场名称。
- 嘉宾职位、介绍和演讲主题。
- 票种名称、权益、报名表字段与条款。
- FAQ、通知模板和发票说明。

内容模型会保留默认语言文本，并为其他语言存储独立版本、翻译状态和更新时间。发布流程必须校验当前大会声明支持的语言，缺失内容会阻止对应语言发布。

## 区域能力

全球化还需要独立推进以下能力：

- IANA 时区和按大会时区展示。
- ISO 4217 货币与按订单固化的小数位规则。
- 国际电话号码输入、规范化和区域短信提供商。
- 区域支付适配器、退款语义和 Webhook 校验。
- 国家、地区和地址格式。
- 税务字段、发票类型和隐私同意文本。
- 数据驻留、保留期限、导出和删除流程。

## 分阶段计划

### 阶段 0：基础设施

- 建立 Vue I18n、语言解析器和类型化翻译目录。
- 提取全局布局、登录、错误页和通用组件文案。
- 建立日期、数字、货币和时区格式化工具。
- 在 CI 中检查语言键一致性、未使用键和直接写入组件的新增文案。

完成标准：管理后台框架可以在 `zh-CN` 与 `en-US` 之间切换，通用界面没有缺失键。

### 阶段 1：管理后台完整覆盖

- 按大会、报名、订单、发票、模板、设置和审计逐域迁移。
- 改造前端错误映射，API 补齐稳定错误代码和参数。
- 增加用户语言偏好与组织默认语言设置。
- 为两种语言建立桌面和移动端视觉回归基线。

完成标准：后台所有可达路由通过语言覆盖率、功能测试和视觉回归；语言切换不丢失表单状态。

### 阶段 2：通知与大会前台

- 让 Worker 按参会者语言渲染通知。
- 支持大会前台语言路由和本地化业务内容。
- 增加本地化 SEO、站点地图和分享信息。
- 建立翻译内容的审核、发布和回滚流程。

完成标准：参会者可以使用一种语言完成浏览、报名、支付、收票、通知和核销说明。

### 阶段 3：区域适配器

- 增加国际手机号、短信和邮件提供商。
- 增加区域支付、货币、税务和地址能力。
- 完成目标市场的隐私与数据生命周期配置。

完成标准：每个声明支持的地区都有端到端验收清单和生产部署说明。

## 发布门禁

每个新增语言需要满足以下条件：

- 翻译键覆盖率为 100%，没有占位文本。
- 登录、导航、核心表单、错误处理和权限流程通过自动化测试。
- 日期、货币、复数和长文本在目标语言下通过视觉检查。
- API 错误不依赖中文消息匹配。
- 通知模板有真实长度和退订场景验收。
- README、部署文档和隐私说明准确描述该语言与地区的支持范围。
