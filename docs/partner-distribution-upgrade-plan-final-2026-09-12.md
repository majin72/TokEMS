# TokEMS 合作伙伴与分销升级最终方案

版本：v3.0，近期架构复核版，待用户确认

日期：2026-09-12

评审基线：本地 `main` 的 `434fcac41ea6f93bcfb190f16a4aef10af991097`，远端 `origin/main` 的 `0d5c1c12737e96018112150cdac0558dfd163933`

替代文件：`docs/partner-distribution-upgrade-plan-final-2026-09-09.md`

本版结合多人购票、订单明细、按参会人退款、支付恢复、发票短信直达、账号服务中心、后台信息架构、公开路由与生产发布规则完成复核。本轮只更新方案，不修改业务代码、数据库、运行服务或微信商户配置，不进行真实转账。

## 1. 最终建议

TokEMS 在普通用户账号上增加大会级“合作伙伴”资格。新注册用户默认没有该资格，由管理员按大会开通。合作伙伴确认当期规则后，可以维护独立公开资料、生成分销链接和海报、查看佣金、申请提现。合作伙伴资格与报名、购票、参会身份分别管理，未购票用户也可以成为合作伙伴。

完整产品包含五个入口：

1. 大会首页的合作伙伴模块、目录与详情页。
2. 个人中心的合作伙伴中心、资料编辑、推广素材、收益和提现页面。
3. 后台用户列表中的大会级快速开通与批量操作。
4. 大会后台中的分销管理模块。
5. 组织后台微信支付设置中的商家转账能力。

技术实现继续采用 Nuxt、Vue、NestJS、PostgreSQL、Redis、BullMQ、MinIO 和 Transactional Outbox。新增部署服务数为 0。佣金作为独立财务域异步处理，购票支付和出票主链路不等待佣金计算。

首期交付完整的推广、计佣、审核、人工结算闭环。第二期接入微信支付新版“商家转账”，由用户逐笔确认收款。两个阶段均可单独上线和回退。

| 产品参数 | 推荐默认值 |
| --- | --- |
| 开通 | 管理员按大会开通；合作伙伴确认规则后接受新归因 |
| 公开 | 总公开、联系方式和海报字段分别授权，默认关闭 |
| 佣金 | 大会默认固定 10%；后台支持订单数阶梯和个人固定比例 |
| 归因 | 30 天内最后一次有效主动点击；创建购买意图时锁定 |
| 订单计数 | 一笔结算订单计为一单；5 人批量购票仍计一单 |
| 计佣颗粒度 | 订单级归因，订单明细级计算、退款冲正与自购排除 |
| 结佣时间 | 支付满 7 天与该订单退款窗口结束后满 24 小时取较晚值 |
| 提现 | 税前可提现金额满 10 元可申请；财务审核后进入批次 |
| 出款节奏 | 用户可随时申请，财务按周或按月批次处理，具体由组织配置 |
| 微信资金 | 由主办方微信支付运营账户提供资金，系统展示核验时间和在途占用 |
| 渠道额度 | 读取并保存当前商户实际获批额度；超限排队或经用户重新确认后改用人工渠道 |
| 推广层级 | 一级合作伙伴，不发展下级，不计算团队佣金 |
| 币种 | 首期只支持人民币 |
| 合作主体 | 合作关系绑定普通用户；个人与企业收款按不同渠道、合同和凭证处理 |

这些比例、期限和门槛属于产品默认值。上线前由主办方确认合同、财务和税务口径。微信准入、额度和场景以目标商户后台的实际批准结果为准。

业务前提：主办方是售票主体和佣金付款主体，并使用自己的普通微信商户号直连出款。若未来由平台替多个独立售票商户统一收款和结算，支付主体、合同关系、税务责任和平台资质都需要重新设计，当前方案不直接沿用。

## 2. 本轮复核结论

v2.0 的五个入口、一级推广、版本化规则、独立账本、人工结算优先和微信逐笔确认方向可以保留。近期系统迭代改变了订单、退款、账户和运维边界，以下内容升级为 v3.0 的强制实施口径。

| 复核发现 | v3.0 处理 |
| --- | --- |
| 订单已支持 1 至 20 人批量购买，并新增稳定的 `order_items` | 佣金增加订单明细分配层。订单保存归因和汇总，明细保存票种资格、基数、佣金、自购判断与退款冲正 |
| 退款已经按 `refund_item_allocations` 分配到具体参会名额 | `RefundSucceeded` 只作为触发信号，财务消费者必须查询真实退款分配，不按订单总额平均摊分 |
| 购票人与参会人分离，参会人可在付款后认领名额 | 购票人是伙伴时整单排除；伙伴成为某个明细的参会人时只排除该明细；身份较晚确认时追加冲正 |
| 新的购买意图通常创建新订单，关闭订单不会作为下一次购买的常规容器 | 网络幂等重试和安全的支付恢复沿用原归因；关闭后重新报名创建新购买意图、新订单和新归因版本 |
| 支付成功以订单级 `settledPaymentId` 和可信支付事实为准 | 支付尝试绑定归因版本；消费者用 `settledPaymentId`、购买意图和订单版本定位唯一规则快照 |
| 个人中心已升级为参会名额、订单、发票和常用资料组成的服务中心 | 合作伙伴作为有资格用户可见的独立服务卡片和独立路由，不挂靠某条报名记录 |
| 发票已支持短信直达、短链接、对象存储和访问审计 | 结算单、税务资料、人工凭证和微信回单复用私有文件能力，使用登录态和专用短期令牌，不复用发票公开直达规则 |
| 后台已有稳定的组织管理区与大会工作区 | 分销放入大会业务管理的二级模块，不继续增加一级导航；组织侧只承载商户能力和凭据设置 |
| 用户可随时提现的模型缺少运营批次和商户额度协调 | 增加组织商户级出款批次、截止时间、预算占用、额度排队和失败恢复 |
| v2.0 缺少“少算、漏算、错算”的正式申诉入口 | 增加佣金申诉，管理员通过不可变调整单处理，禁止直接覆盖历史归因和金额 |
| 资格状态同时承担公开、归因和结算控制，容易误伤已产生权益 | 拆分资格、公开状态、新归因开关、结算暂停和收款人状态 |
| 微信转账状态和默认额度描述不完整 | 补齐新版商家转账状态、必填报备信息、24 小时确认、30 天查单和对账兜底 |
| `/partners`、`/r` 和 `/payout` 尚未进入保留路由及统计边界 | 同步更新路由保留字、公开统计分类、敏感页面新文档边界和网关测试 |
| 公开详情页需要与当前嘉宾、会员详情保持一致 | 固定复用 `FlowHeader` 和现有人物详情结构，左侧资料，右侧大会卡片、海报和报名按钮 |

本地 `main` 与 `origin/main` 当前存在少量提交差异，主要是发票下载链接修复的提交整理和发布记录。两条基线均已纳入本轮阅读，差异不改变本方案的领域设计。

## 3. 范围与边界

### 3.1 本期范围

- 管理员按大会开通、暂停、关闭合作伙伴资格。
- 合作伙伴规则确认、资料管理、逐字段公开和海报授权。
- 大会首页合作伙伴区块、公开目录和人物详情页。
- 稳定推广链接、二维码、海报、有效访问聚合和订单归因。
- 固定比例、订单数阶梯、个人固定比例和票种排除。
- 批量订单的明细级佣金计算、部分退款冲正和延迟自购识别。
- 待结算、可提现、冻结、处理中、已支付、冲正和待追偿账本。
- 用户提现申请、财务审核、出款批次、人工结算、凭证和对账。
- 第二阶段微信新版“商家转账”、用户确认、回调、主动查单和资金账单对账。
- 佣金申诉、审计、通知、权限和运营指标。

### 3.2 本期明确不做

- 多级分销、团队佣金、下级招募和裂变层级。
- 一个订单拆给多个推广伙伴。
- 外部联盟平台自动同步。
- 储值钱包、余额消费、垫资和资金池产品。
- 自动生成税率或代替财务作税务判断。
- 对上线前历史订单自动补佣。
- 多币种和跨境支付。
- 未经审核的全自动出款。
- 通过拆单规避微信单笔或单日额度。
- 伙伴直接修改订单推荐人。

## 4. 产品入口与页面

### 4.1 大会首页、目录和详情页

大会首页增加“大会合作伙伴”区块，放在合作机构附近。机构 Logo、报名会员和个人合作伙伴分别维护。首页默认展示 12 人，目录每页 24 人，排序依据依次为管理员排序值、发布时间和稳定 ID。

公开条件同时满足：

- 大会启用合作伙伴展示。
- 伙伴资格有效。
- 公开状态为已发布。
- 普通账号状态正常。
- 用户同意公开。
- 展示名和一句介绍已经填写。
- 管理员未隐藏资料。

公开详情页沿用当前嘉宾和会员详情页的排版与组件：

- 顶部保留大会菜单栏和 `FlowHeader`。
- 左侧展示头像或个人图片、姓名、公司、职位、标签、个人介绍和获准公开的联系方式。
- 允许上传一张个人主图及少量介绍图片，图片需有替代文本。
- 右侧展示大会卡片、个人推广海报、二维码和“通过我报名”按钮。
- 普通浏览只查看资料，不写入推荐来源。“通过我报名”按钮进入 `/r/{code}` 后才建立归因。
- 外部联系方式链接带 `nofollow ugc noopener noreferrer`，电话、邮箱和微信号按字段授权。

推荐路由：

- `/partners?event={eventSlug}`：合作伙伴目录。
- `/partners/{publicSlug}?event={eventSlug}`：合作伙伴详情。
- `/r/{code}`：推广入口。

详情页在草稿和待审核阶段使用 `noindex,nofollow`。正式发布后默认 `index,follow`，大会可统一关闭搜索收录。规范网址不包含推广码、来源参数或个人敏感字段。

资料撤回后，目录、详情和新素材生成立即停止。受控图片地址短期失效。系统在首次公开和下载海报前说明，已经下载、截图或被第三方缓存的内容可能继续存在。

### 4.2 个人中心合作伙伴中心

在当前个人中心服务区增加条件卡片“合作伙伴中心”。用户拥有任一大会的合作关系时显示。推荐路由为 `/account/partnerships/:eventId`，用户无需报名或购票即可访问。

| 页面 | 解决的问题 |
| --- | --- |
| 合作伙伴概览 | 查看资格、规则版本、资料完整度、推广数据、待结算和可提现金额 |
| 我的资料 | 维护头像、图片、展示名、公司、职位、行业、介绍、网站、电话、邮箱和微信号 |
| 公开与海报授权 | 分别选择官网、联系方式和海报可用字段，预览真实公开效果 |
| 推广素材 | 复制稳定链接，下载二维码和 1080×1440 海报，查看规则与禁用原因 |
| 推广收益 | 查看订单级摘要、明细级计佣、退款调整、释放日期和状态解释 |
| 提现与收款 | 绑定收款人，申请提现，确认税前、税费和实付金额，完成微信确认 |
| 结算记录 | 查看人工凭证、微信结果、失败原因、对账结果和可下载结算单 |
| 佣金申诉 | 对漏单或金额异议提交订单号、日期和证据，查看处理结果 |

资料可以从常用资料或参会名片主动复制，复制后独立保存。后续修改参会资料不自动覆盖合作伙伴资料。管理员可以隐藏不适当内容或要求修改，不能替用户扩大公开范围。

暂停新归因后，用户仍可查看历史收益、申诉和结清。关闭公开展示不影响已经合法形成的佣金。

### 4.3 后台用户列表快速开通

组织用户列表增加“合作伙伴”列和行内操作。操作时必须选择大会，避免把组织级用户关系误解为全组织通用资格。

开通抽屉包含：

- 目标大会。
- 继承大会规则或使用个人固定比例。
- 公开排序。
- 内部备注。
- 是否立即发送邀请通知。
- 生效规则摘要和条款版本。

批量开通显示目标大会、选中人数、成功数、失败数和逐项原因。操作具有幂等性，重复提交不会创建第二条伙伴关系。

普通“合作申请”继续作为意向收集。管理员完成账号匹配并开通后才形成合作关系。未注册申请人需要先注册，系统不根据申请手机号创建可提现账户。

### 4.4 大会后台分销管理

新增大会路由 `/events/:eventId/distribution`。入口放在报名与交易相关的二级业务区，保持现有大会工作区的一级导航结构。

模块包含五个标签：

| 标签 | 核心能力 |
| --- | --- |
| 概览 | 净成交额、佣金负债、待结算、可提现、在途、已支付、冲正、申诉和异常 |
| 合作伙伴 | 资格、公开预览、排序、个人比例、规则接受记录、新归因开关和结算暂停 |
| 佣金订单 | 订单、购买意图、支付、订单明细、计佣基数、档位、退款分配和调整记录 |
| 提现与对账 | 审核、出款批次、微信确认、人工凭证、主动查单、资金账单和差异处理 |
| 分销设置 | 总开关、票种、规则、等待期、门槛、条款、推广规范、海报和公开区块 |

伙伴列表和订单列表只展示完成运营所需的信息。合作伙伴看不到购票人姓名、手机号、证件、参会人隐私或支付标识。后台导出继续受专用财务权限、用途记录和审计控制。

### 4.5 组织后台商家转账设置

在 `/manage/settings/payment` 的现有微信支付集成中增加“商家转账”能力区。继续使用 `organization_integrations` 的加密凭据、密钥版本、配置修订和最近核验时间，不建立第二套明文凭据库。

设置包括：

- 能力启停。
- 绑定 AppID 和商户号。
- 已获批场景，首期使用 `1005` 佣金报酬。
- 商户平台实际额度和最近核验时间。
- 通知地址、出口 IP 和验签配置状态。
- 出款周期、批次截止日和预算。
- 运营账户余额人工或接口核验时间。
- 活跃出款存在时的配置修改锁。

大会管理页只读取能力、预算和额度状态，不展示私钥、APIv3 Key、AppSecret 或完整收款标识。

## 5. 领域状态与控制开关

### 5.1 独立状态维度

一条合作伙伴关系使用以下独立维度，避免一个状态同时改变公开、归因和结算权益。

| 维度 | 状态或字段 | 含义 |
| --- | --- | --- |
| 资格 | `pending_confirmation`、`active`、`paused`、`closed` | 合作关系生命周期 |
| 公开 | `draft`、`published`、`hidden` | 官网是否展示 |
| 新归因 | `attribution_enabled` | 是否接受新的推广归因 |
| 结算 | `settlement_hold` 与原因 | 是否暂缓佣金释放和提现 |
| 收款人 | `unbound`、`pending`、`verified`、`disabled` | 微信或人工收款身份状态 |
| 海报 | 独立字段授权和素材版本 | 是否允许把资料印入海报 |

资格暂停默认关闭新归因并隐藏公开资料，已经锁定的合法订单继续按规则计算。风控调查可以单独暂停结算。资格关闭保留历史财务记录和最终结清入口。

### 5.2 佣金状态

佣金头记录采用以下状态：

`provisional` → `pending` → `available` → `reserved` → `paid`

异常分支包括 `held`、`reversed`、`partially_reversed` 和 `recovery_due`。

- `provisional`：支付已确认，参会人身份或退款事实仍可能变化。
- `pending`：计算已完成，等待退款窗口和观察期。
- `available`：可以申请提现。
- `reserved`：已被提现申请或出款批次占用。
- `paid`：渠道明确成功并完成本地对账。
- `held`：风险、争议、资料或税务条件需要人工处理。
- `recovery_due`：已支付后发生退款或确认自购，形成待追偿余额。

状态由不可变账本分录驱动，汇总余额可以重建。管理员不能直接编辑余额字段。

### 5.3 提现与出款状态

提现申请状态：

`submitted` → `under_review` → `approved` → `batched` → `executing` → `succeeded`

可进入 `rejected`、`cancelled`、`failed` 或 `unknown`。`unknown` 持续占用金额，查明原渠道终态前不允许换单号或换渠道重复支付。

微信执行记录完整映射官方状态：`ACCEPTED`、`PROCESSING`、`WAIT_USER_CONFIRM`、`TRANSFERING`、`SUCCESS`、`FAIL`、`CANCELING`、`CANCELLED`。只有 `SUCCESS` 计为到账。

## 6. 归因与购买意图

### 6.1 推广入口

推广链接使用本站 `/r/{code}`。`code` 为不可猜测的随机码，固定绑定组织、大会和合作伙伴。服务端校验资格、规则接受、有效期和目的地，不接受客户端提供伙伴 ID、比例、余额或任意跳转地址。

有效主动访问建立 30 天第一方归因上下文。Cookie 使用 HttpOnly、Secure、SameSite=Lax、主机限定和服务端到期时间。自然访问、普通详情浏览、无效码和机器人预取不覆盖已有合法来源。

报名确认页显示当前推荐来源并允许用户清除。若伙伴资料保持私密，只显示“合作伙伴推广链接”。用户清除后，系统保存明确的无归因原因。

微信内缺少可靠导航信息时显示轻量确认页，由一次同源操作建立来源。首期不使用设备指纹。跨设备用户需要重新打开链接或扫码。

### 6.2 不可变归因版本

新增 `partner_attribution_revisions`。每个购买意图和订单版本保存一次不可变归因决策，包含：

- 组织、大会、伙伴和推广访问引用。
- `purchaseIntentId`、订单 ID、`orders.version`。
- 明确的有归因或无归因结果及原因。
- 规则版本、个人比例版本、有效票种和等待期。
- 购票人身份快照和当时已知的参会人身份。
- 金额、币种、票种和订单明细快照。
- 创建时间、有效期和审计来源。

支付尝试引用 `attributionRevisionId`。支付成功后以 `settledPaymentId` 解析唯一归因版本。迟到通知、换渠道和重复通知不能把资金归到另一个版本。

| 当前系统场景 | 归因处理 |
| --- | --- |
| 首次创建购买意图和订单 | 按当前合法来源创建归因版本并锁定 |
| 同一 `purchaseIntentId` 的网络重试 | 返回同一订单和同一归因版本 |
| 原订单安全恢复、切换支付渠道或换设备继续支付 | 沿用原订单和归因版本 |
| 订单关闭或取消后重新报名 | 创建新购买意图、新订单和新归因版本 |
| 旧支付结果仍不确定 | 继续执行现有支付门禁，禁止建立可能重复支付的新结算事实 |
| 支付后参会人认领或修改资料 | 归因伙伴不变；明细自购资格可以触发追加调整 |
| `modelVersion=1` 历史订单 | 不自动追溯计佣；受控补记需要证据、审批和调整分录 |

批量购票当前通常使用同一票种和单价，数据模型已具备稳定的订单明细。佣金从首版即按明细计算，为后续混合票种、部分退款和参会人识别保留正确边界。

## 7. 佣金规则与批量订单

### 7.1 规则版本

大会分销规则使用不可变版本。每次发布保存完整配置和条款内容哈希，包括：

- 固定比例或订单数阶梯。
- 可参与票种。
- 归因期限。
- 结算等待期。
- 最低提现金额。
- 退款、取消、自购和争议处理规则。
- 推广渠道规范和禁用行为。
- 税前金额、代扣和调整说明。
- 生效时间、过渡期和发布人。

个人固定比例优先于大会默认比例，票种资格仍然适用。比例使用万分位整数，范围为 0 至 100%。新票种默认不参与，发布新规则后才能加入。

降低比例、延长等待期或改变经济条件时创建新版本，默认提前 7 天通知。用户接受后，新购买意图使用新版。过渡期内未接受的用户继续按已接受旧版建立归因；过渡期结束后暂停新归因。历史订单不重算。

### 7.2 阶梯计算

阶梯按本大会、同一伙伴、符合规则且尚未全额退款的已支付订单数计算。一笔 5 人订单计为一单。部分退款保留该订单的一次计数，全额退款撤销一次计数。已经分配给历史订单的比例不重新排序，退款产生单独冲正。

档位由财务消费者首次成功处理支付时分配。同一伙伴在短事务内加锁，生成稳定序号。重试读取已有结果。支付事件到达顺序和支付时间都保留供后台解释。

若业务最终希望按成功参会名额数量走阶梯，需要发布另一种规则类型并修改条款。本期不混用两种口径。

### 7.3 明细级计佣

一笔订单创建一个 `partner_commissions` 汇总记录，每个 `order_item` 创建一条 `partner_commission_items`。明细保存票种、单价、可计佣金额、比例、佣金、排除原因、退款分配和状态。

计佣基数为符合规则的订单明细成交分配金额减该明细累计成功退款金额。所有金额使用整数分，比例使用万分位整数。总佣金等于明细佣金之和，舍入规则固定在规则版本中，推荐逐明细向下取整到分。

微信 `amount.total`、`payer_total`、站内订单成交额和商户净入账分别保存。默认佣金基数使用站内核验成功的成交分配金额。微信优惠由平台承担时，`payer_total` 不替换成交基数。将来增加站内补贴、组合支付或多币种时需发布新的金额规则。

示例：5 人订单共 5,000 元，其中 1 个名额属于不参与分销的票种或后来确认由伙伴本人参会。该明细排除，剩余 4,000 元按 10% 计佣，佣金为 400 元。若其中一个 1,000 元明细后来全额退款，追加 100 元负向调整，剩余佣金为 300 元。

### 7.4 自购、代购和较晚认领

- 伙伴本人是购票人时，整笔订单不计佣。
- 购票人不同，但某个订单明细的已验证参会人是伙伴时，只排除该明细。
- 批量下单时参会人身份未知，先标记为暂定，释放前和出款前再次核验。
- 付款后认领名额确认伙伴本人受益时，追加该明细的负向调整，不覆盖原归因记录。
- 已经出款后确认自购或发生退款，生成待追偿余额。后续可提现佣金优先抵扣；现金追偿和税务调整由财务分别记录。
- 同手机号、同收款人、重复设备或网络只作为风险信号。系统不凭单一信号自动没收佣金。

关联关系无法可靠确认时进入人工审核。审核证据、决定、操作者和时间写入审计记录。

### 7.5 退款和冲正

`RefundSucceeded` 事件用于唤醒财务消费者。消费者从数据库读取 `refund_requests`、`refund_request_items` 和 `refund_item_allocations`，核验退款终态后按真实明细分配冲正。

- 待结算佣金直接减少。
- 可提现但未申请的佣金通过负向账本分录减少。
- 已被提现占用的佣金暂停该申请并重新计算。
- 渠道执行已进入不可撤销阶段时继续查明结果，成功后形成追偿余额。
- 同一退款分配只处理一次，重复事件返回已处理结果。

佣金释放条件为支付满 7 天与订单退款窗口结束后满 24 小时取较晚值。订单、退款、争议、身份和财务收件箱存在异常时继续冻结。

## 8. 财务账本、提现和申诉

### 8.1 账本

账本采用只追加分录，至少记录：

- 佣金产生。
- 退款冲正。
- 自购排除调整。
- 人工纠错。
- 提现占用与释放。
- 税费扣减。
- 实际出款。
- 已付款后的追偿。

每条分录包含业务键、组织、大会、伙伴、订单、订单明细、规则版本、金额、币种、来源事件、证据引用和审计信息。数据库唯一键阻止重复记账。余额是分录聚合结果，并保留可重建的物化汇总。

伙伴端展示待结算、预计可用日期、可提现、审核中、待用户确认、已到账、冲正和待抵扣。预计日期清楚标记为预计值。

### 8.2 提现申请与批次

用户可以随时提交提现申请。系统先占用可提现余额，保存不可变结算明细。财务按组织、商户、币种和截止时间创建 `partner_payout_batches`，建议初始按周处理，后台可改为月度。

出款批次承担：

- 预算占用。
- 商户单笔、单用户、单日和月度额度校验。
- 审核分工。
- 出款排序和重试节奏。
- 资金余额核验。
- 统一对账和关闭。

批次只是本地运营分组。微信接口仍为一位用户一笔商家转账单。系统不把多个收款人合成一笔渠道请求。

每次出款前，用户确认税前佣金、税费、实付金额、收款人和渠道。结算金额、税费或收款人变化后重新确认。未确认的申请不提交渠道。

### 8.3 人工结算

第一阶段采用人工银行转账或其他主办方批准的线下方式。财务先锁定执行记录和幂等业务号，再完成外部打款，随后上传回单、录入流水号和到账时间。

执行结果不明时保持 `unknown` 并占用金额。核验银行或原渠道结果后才能重试。人工凭证使用私有对象存储、文件哈希、访问审计和权限控制。

### 8.4 佣金申诉

合作伙伴可以提交“漏单”或“金额异议”，填写订单号、购买日期、问题类型、说明和证据。伙伴不能在申诉中指定另一位伙伴或直接修改归因。

管理员处理结果为：

- 已有记录解释，无金额调整。
- 证据不足，驳回并说明原因。
- 确认漏记，创建补记调整。
- 确认多记，创建冲正调整。

申诉、证据、决定、关联调整、处理人和处理时间完整审计。申诉期间可以只冻结争议金额，其他已确定金额继续结算。

### 8.5 税务口径

系统保存税前佣金、财务核定税费、实付金额、付款主体、收款主体、税期、项目、已扣和调整依据。税率、申报方式和凭证类型由主办方财务依据合同、收款人身份和当期政策核定，代码不硬编码个人劳务报酬税率。

同一付款主体、收款主体、税期和项目可能需要合并核算。已支付后发生退款时，佣金冲正、现金追偿和税额调整分别记账。税务结果未核定时暂停相关抵扣出款。

合作关系始终绑定普通用户账号，资料中的公司名称不自动把收款主体变为企业。自然人通过微信商家转账或人工渠道收款。企业结算需要单独核验企业名称、合同、对公账户和发票，并走人工结算；本期微信商家转账不承担企业对公付款。

税务与凭证实施时以国家税务总局现行规则和主办方财务意见为准：

- [中华人民共和国个人所得税法实施条例](https://www.chinatax.gov.cn/n810219/n810744/n3752930/n3752974/c3963364/content.html)
- [个人所得税扣缴申报管理办法（试行）](https://www.chinatax.gov.cn/n810219/n810744/n3752930/n3752974/c3963396/content.html)

## 9. 微信商家转账

### 9.1 接入方式

第二阶段接入微信支付新版“商家转账”，使用普通商户接口 `/v3/fund-app/mch-transfer/transfer-bills`。首期场景为 `1005` 佣金报酬，并按官方要求提供两条报备信息：`岗位类型` 和 `报酬说明`。具体用户感知文案由主办方财务确认。

微信 HTTP 请求成功只表示受理结果。系统以回调验签后的终态、主动查单和资金账单为事实来源。前端 `requestMerchantTransfer` 成功回调只表示页面流程完成，不表示已经到账。

### 9.2 用户确认和超时

用户通过微信内页面确认收款。官方流程给用户约 24 小时确认，实际关闭可能晚于 24 小时。系统在超时后先查原商户单号，再决定是否取消或重新发起。

同一逻辑出款使用稳定商户单号和幂等键。只有原单明确进入 `FAIL` 或 `CANCELLED`，且本地确认可重试时，才创建新执行版本。`PROCESSING`、`WAIT_USER_CONFIRM`、`TRANSFERING`、`CANCELING` 和本地 `unknown` 都禁止换单号重付。

微信商家转账查单可用期为 30 天。超过后使用资金账单和本地证据完成对账。Worker 在等待期内主动查单，终态后停止轮询。

### 9.3 回调安全

回调入口使用原始请求体完成签名验证，校验 `Wechatpay-Serial`、时间戳、随机串和签名，再用 APIv3 Key 按 AES-256-GCM 解密。重复回调允许安全重放。

处理顺序：

1. 验签、时效和商户归属校验。
2. 保存原始通知摘要和唯一事件键。
3. 在持久化成功后返回 HTTP 200 或 204。
4. 异步更新执行状态和账本。
5. 关键字段冲突时进入主动查单和人工核验。

回调缺失时由定时查单兜底。回调、查单和账单三路事实出现差异时，保持资金占用并禁止重复支付。

### 9.4 额度与资金

截至本方案复核时，微信官方普通商户文档列出的常见默认额度包括：单笔 200 元、同一用户单日 2,000 元、商户单日 50,000 元、商户月度 30,000,000 元。部分额度可以在商户平台申请调整，目标商户的实际值可能不同。

系统在配置时保存实际获批额度和核验时间，在每次组批及提交前再次校验。大于实际单笔额度的申请进入待处理状态，财务可以等待额度调整，或在用户重新确认渠道和金额后改用人工转账。系统不自动拆单绕过渠道限制。

商家转账从微信支付运营账户出款。主办方需要预先充值，并保留退款和日常支付所需资金。后台分开展示系统账面负债、本地预算占用、渠道在途和最近核验的运营账户余额，避免把非实时余额当作到账承诺。

### 9.5 收款身份

合作伙伴的 OpenID 绑定使用独立 OAuth 目的、短期 state、一次性消费和近期登录验证，不复用订单支付身份。绑定时记录 AppID、OpenID 的受控标识、用户、组织、用途和验证时间。

收款人姓名等敏感字段按渠道要求加密传输和加密存储，日志只保留脱敏值。更换收款人时撤销未提交执行并重新审核；已经提交的执行继续按原快照查明终态。

## 10. 推广治理与风险控制

大会规则需要明确允许渠道和禁用行为，至少覆盖：

- 伙伴本人或本人受益明细不计佣。
- 禁止虚假宣传、价格承诺、垃圾消息、冒用大会身份和未经授权使用个人信息。
- 品牌关键词投放、优惠码传播和付费广告由大会逐项选择是否允许。
- 公开内容、海报和联系方式由伙伴确认授权。
- 风险调查、申诉、暂停和恢复流程。
- 资格关闭后的历史收益和最终结清方式。

风险信号包括短时间异常点击和下单、同一购票人或收款人高度重复、相同设备或网络聚集、异常高退款率、多人认领关系冲突和重复收款身份。信号进入评分和人工复核，不直接形成没收决定。

暂停新归因、隐藏公开资料、冻结结算和关闭资格分别操作。每次操作需要原因、范围、证据、操作者和恢复条件。伙伴可以对结算决定发起申诉。

## 11. 权限模型

新增细粒度员工权限：

| 权限 | 能力 |
| --- | --- |
| `event.partner.read` | 查看大会伙伴资料和状态 |
| `event.partner.manage` | 开通、暂停、关闭、排序和隐藏伙伴 |
| `event.partner.rules.manage` | 发布规则、条款、票种和海报配置 |
| `event.commission.read` | 查看订单、佣金和调整摘要 |
| `event.commission.manage` | 处理佣金申诉和受控调整 |
| `event.payout.review` | 审核提现和税务资料 |
| `event.payout.execute` | 创建出款批次、提交渠道、处理失败 |
| `event.payout.export` | 导出财务和对账资料 |
| `org.payout.settings.read` | 查看组织商家转账能力 |
| `org.payout.settings.manage` | 修改凭据、额度、预算和出款策略 |

用户列表快速开通需要 `customer.read` 和 `event.partner.manage`。大会负责人默认获得伙伴资料管理和佣金摘要查看权限，默认不获得出款执行和财务导出权限。

涉及员工本人、已知关联收款人或相同物理身份的提现，由另一位有权限人员审核。员工 `users` 和普通用户 `customer_users` 使用不同表，检查时通过已验证手机号、绑定收款人和受控关系映射识别，不能只比较 UUID。

高风险操作需要近期验证、双人复核或第二人执行：修改商户凭据、提高预算、批量审核、出款提交、未知状态改判、财务导出和大额人工调整。

## 12. 数据模型

计划新增 18 张业务表，均带组织和大会边界、创建时间、版本及必要审计字段。迁移从当前最高迁移之后顺序新增，实施时以仓库实际编号为准。

| 表 | 作用 |
| --- | --- |
| `event_partner_program_versions` | 不可变大会规则、条款、推广规范、内容哈希和生效时间 |
| `event_partners` | 大会与普通用户关系，保存资格、公开、新归因、结算和当前规则指针 |
| `event_partner_profile_versions` | 伙伴资料、图片、公开字段和海报字段的版本历史 |
| `event_partner_rule_acceptances` | 用户接受的规则、条款哈希、身份和时间 |
| `partner_referral_links` | 稳定推广码、目的地和启停状态 |
| `partner_referral_visit_days` | 去重后的按日访问聚合 |
| `partner_attribution_revisions` | 购买意图与订单版本的不可变归因决策 |
| `partner_financial_event_inbox` | 支付、退款、认领和订单事实的独立幂等收件箱 |
| `partner_commissions` | 每个结算订单的佣金汇总、档位和状态 |
| `partner_commission_items` | 每个订单明细的基数、资格、退款、自购与佣金分配 |

| `partner_payout_recipients` | 加密收款身份、OpenID 绑定状态和版本 |
| `partner_payout_requests` | 用户提现申请和不可变结算明细 |
| `partner_payout_batches` | 组织商户级出款批次、额度、预算、截止时间和对账状态 |
| `partner_payout_executions` | 每次人工或微信执行、幂等键、渠道单号和状态快照 |

| `partner_commission_inquiries` | 漏单和金额异议、证据、决定及关联调整 |

关键约束：

- `event_partners` 对组织、大会、普通用户唯一。
- 每个订单只允许一个有效归因伙伴。
- 每个订单和归因版本只允许一个佣金头记录。
- 每个佣金头与订单明细只允许一条基础佣金分配。
- 账本业务键、财务收件箱事件键、提现占用键和渠道提交键全局幂等。
- 出款执行保存所用集成修订、密钥版本、规则、收款人、金额和报备信息快照。
- 删除普通账号前检查伙伴关系、未结清账务、提现和申诉；需要保留的财务主体使用受控快照，不依赖账号记录永久存在。

不在 `orders`、`order_items`、`payments` 和 `refunds` 中复制可编辑佣金余额。业务表通过稳定 ID 关联，消费者每次核验真实支付和退款事实。

## 13. 服务、事件和接口

### 13.1 服务边界

在现有 NestJS 模块化单体内新增 Partner Distribution 模块，包含资料、归因、佣金、提现、出款、对账和申诉服务。Worker 增加独立队列和扫描任务。支付、出票、退款主事务继续只发布可信事件。

财务消费者使用自己的 `partner_financial_event_inbox`。Outbox 的“已发布”不代表佣金“已处理”。消费者处理完成后独立记录结果和重试次数。遗漏扫描用 `settledPaymentId`、支付终态和退款分配反查，补齐缺失事件。

统一短事务锁顺序建议为：伙伴汇总 → 佣金头 → 佣金明细 → 提现申请 → 出款执行。外部微信请求不在数据库锁事务内执行。

### 13.2 事件口径

- `PaymentSucceeded`：触发订单级佣金建立。消费者查询订单、支付、购买意图和全部订单明细。
- `RefundSucceeded`：触发明细级冲正。消费者查询退款终态和 `refund_item_allocations`。
- 参会人认领或解绑事件：触发明细自购资格复核。
- 资格或规则事件：控制新归因和通知，不改写历史佣金。
- 提现、渠道回调和查单事件：驱动出款状态和账本。

支付成功事务不调用佣金计算服务。佣金消费者失败时，支付、出票和票证保持现有成功结果，后台显示财务积压并暂停相关提现释放。

## 14. 路由、统计、文件和隐私

### 14.1 公开与敏感路由

在 `RESERVED_PUBLIC_EVENT_SLUGS` 增加 `partners`、`r` 和 `payout`，并同步前端、API、网关和规范路由测试。

- `/partners` 属于公开内容页，可按现有公开统计规则加载统计脚本。
- `/r` 属于归因操作页，全流程不加载第三方统计。
- `/account/partnerships`、`/payout` 及所有收款、账务和申诉页属于敏感区，不加载第三方统计。
- 从公开页进入敏感区或从敏感区返回公开页时创建新文档，防止第三方脚本和敏感页面内存跨越边界。
- 对外跳转地址由服务端生成并执行允许列表，拒绝任意 `returnUrl`，外链中移除推广码和敏感参数。

出款首期放在主站登录后的敏感区域，不增加新的 `payout-web` 服务，也不占用现有 `/pay/hui/` 支付页面。只有微信 OAuth 域名配置明确要求独立来源时，才增加受控的 `PAYOUT_PUBLIC_URL`。

### 14.2 私有文件

结算单、税务材料、人工回单和微信回单复用 MinIO 与现有文件服务，使用：

- 登录态和对象级授权。
- 用途专属短期下载令牌。
- `private, no-store` 缓存策略。
- 文件 ID、类型、大小、哈希和版本校验。
- 撤销、访问日志和下载审计。

发票短信直达允许在限定期限内凭短链接访问发票文件。合作伙伴财务文件包含更高敏感信息，不使用该 30 天免登录规则。微信电子回单在来源和哈希校验后保存为结算文档。

### 14.3 数据最小化和留存

- 原始推广技术记录默认保留 7 天，用于限频和去重；之后仅保留无个人身份的日聚合。
- 伙伴端订单只展示脱敏订单号、购买日期、符合规则的金额和状态。
- OpenID、姓名、手机号、证件和银行信息按字段加密或脱敏，禁止进入日志和分析事件。
- 用户撤回公开授权后停止公开读取和新海报生成。
- 财务、合同、税务和审计记录按主办方确认的法定期限保留，账号注销不会清除未结清义务和必要凭证。
- 用户删除流程先完成未支付订单、票证、发票、伙伴账务、提现、申诉和收款身份检查，再决定匿名化或物理删除。

## 15. 通知、对账和运营

### 15.1 通知矩阵

复用现有通知与 Outbox 体系，支持站内消息和已配置的短信能力。通知失败不回滚财务事实。

通知节点包括：

- 合作伙伴邀请、开通、暂停、恢复和关闭。
- 新规则发布、过渡期提醒和接受结果。
- 佣金建立、退款调整、释放和冻结。
- 提现提交、审核、税费确认和组批。
- 微信待用户确认、即将过期、成功、失败和取消。
- 人工打款完成和凭证可用。
- 佣金申诉受理、补充材料和处理结果。

通知内容不包含完整收款身份、证件、购票人资料和可直接重放的下载令牌。

### 15.2 对账

每天执行三类核对：

1. 交易事实：成功支付与佣金头、订单明细是否完整对应。
2. 退款事实：成功退款分配与负向分录是否完整对应。
3. 出款事实：本地执行、微信查单、资金账单和账本是否一致。

差异记录在 `partner_reconciliation_runs`，包含范围、数量、金额、证据、负责人和处理结果。资金差异未关闭时暂停相关批次和新出款。

### 15.3 运营指标

后台关注：

- 有效推广访问、建立归因和支付转化率。
- 净成交额和佣金负债。
- 待结算账龄、可提现账龄和出款服务时长。
- 退款率、自购排除、异常冻结和申诉率。
- 商户额度利用、运营账户核验时间和渠道失败率。
- 回调与主动查单差异、账单对账差额和积压事件数。

访问统计用于运营分析，佣金结算只依据订单、支付、退款、身份和账本事实。

## 16. 成熟分销系统经验的取舍

本版参考成熟系统中与 TokEMS 业务直接相关的做法：

- Dub 的等待期、最低提现额、分批确认、佣金状态、退款与欺诈冲正。
- PartnerStack 的预计收益、可用收益、退款观察期和付款日历。

## 17. 交付阶段

### 17.1 第一阶段：合作伙伴与人工结算闭环

预计 15 至 22 个工程人日，完成：

- 数据表、规则版本、权限和审计。
- 管理员开通与大会分销管理。
- 合作伙伴资料、公开授权、目录和详情页。
- 推广链接、二维码、海报和归因版本。
- 批量订单明细计佣、退款冲正、自购复核和账本。

- 佣金申诉、通知、运营指标和积压监控。

该阶段上线后可以用人工渠道完成真实业务闭环。上线前需要主办方确认规则、条款、推广规范、财务审核人和税务流程。

### 17.2 第二阶段：微信商家转账

预计 8 至 12 个工程人日，完成：

- 商家转账能力配置和安全验证。
- 独立 OpenID 绑定与收款人版本。
- 微信逐笔出款、用户确认页和状态机。

总预计为 23 至 34 个工程人日，不含微信商户审核、合同与税务确认、生产观察期和视觉反馈轮次。

## 19. 验收标准

### 19.1 产品验收

- 未开通用户看不到合作伙伴中心，也不能通过猜测路由取得资料或收益。
- 开通后用户确认规则，能编辑资料、分别授权公开和海报字段。
- 公开详情页保留顶部菜单，排版与嘉宾或会员详情一致，右侧有大会卡片、海报和推广按钮。
- 普通浏览详情不改归因，点击推广按钮才建立来源。
- 管理员可以从用户列表按大会单个或批量开通。
- 大会后台五个标签完整覆盖伙伴、佣金、提现、对账和设置。
- 暂停公开、停止新归因和冻结结算可以分别执行。

### 19.2 交易与佣金验收

- 一笔 5 人订单只占一个阶梯订单序号，并生成 5 条佣金明细。
- 其中 2 个明细退款时，只冲正这 2 个明细的佣金。
- 伙伴本人购票时整单排除；伙伴后来认领其中一个名额时只冲正该明细。
- 同一购买意图的网络重试、支付恢复和换渠道不改变归因。
- 关闭后重新报名创建新购买意图和新归因。
- 重复、乱序和迟到的支付、退款、认领事件不会重复记账。
- 财务消费者停机后补跑可以恢复完整佣金，购票和出票不受影响。
- 上线前历史订单不自动产生佣金。

### 19.3 提现与微信验收

- 两次并发提现不能重复占用余额。
- 出款批次超预算或超实际商户额度时停止提交并说明原因。
- 未知渠道状态下不能换单号、换渠道或再次占用。
- 用户在微信确认页完成操作后，系统继续等待回调或查单终态。
- 回调重复、缺失、乱序、验签失败和解密失败均有明确处理。
- 24 小时确认期结束后先查原单，30 天以后以资金账单对账。
- 单笔超过实际额度时不会自动拆分。
- 人工与微信出款都需要执行记录、凭证、账本和对账结果。

### 19.4 权限、安全与隐私验收

- 大会 A 的管理员不能管理大会 B 的伙伴或佣金。
- 资料管理员不能执行出款，财务查看人不能修改商户凭据。
- 自审和关联收款审核由另一位有权限人员完成。
- 公开 API 不返回未授权联系方式，伙伴 API 不返回购票人隐私。
- `/r`、`/payout` 和账户页不加载第三方统计。
- 公开与敏感区导航创建新文档。
- 结算文件需登录和专用短期令牌，发票短信链接不能访问合作伙伴财务文件。
- OpenID、姓名、证件、密钥和回调明文不进入日志。

### 19.5 性能与运行验收

- 10,000 位合作伙伴、100,000 笔订单和批量明细下的后台列表使用索引和游标分页。
- 财务积压、最老事件年龄、失败次数和对账差异可监控。
- 海报生成异步执行并限制并发，不阻塞资料页。
- 微信请求遵循官方 QPS 和商户额度，批次调度可暂停和恢复。
- 生产发布完成后验证容器健康、本机及公网 HTTP、构建版本、迁移哈希、公开大会内容和生产数据计数。

## 21. 上线、观察与回退

### 21.1 上线顺序

1. 先部署新增表、消费者和只读后台，所有大会开关关闭。
2. 验证支付与退款事件回放、财务收件箱、补账和监控。
3. 对一个内部测试大会启用伙伴资料和人工结算。
4. 完成批量购票、部分退款、自购认领、人工凭证和对账演练。
5. 分大会启用公开目录和推广归因。
6. 微信阶段先用测试伙伴和小额真实转账验收，再按组织启用。

每个大会启用前发布规则和条款，确认负责人、财务审核人、预算、税务流程和申诉渠道。

### 21.2 观察指标

启用后重点观察财务收件箱积压、佣金与支付差异、退款冲正延迟、提现账龄、未知出款、回调缺失、额度阻塞、运营账户余额和对账差额。任何资金差异都暂停相关批次的新出款。

### 21.3 回退

回退采用功能开关：

- 停止新伙伴开通、新公开、新归因和新提现。
- 保留财务消费者处理已经发生的支付、退款和认领事实。
- 保留微信回调、主动查单和对账，直至所有在途执行进入终态。
- 新表和历史账本保持只读，不执行破坏性回滚。
- 活跃微信出款存在时，禁止回退到无法识别其状态和回调的应用版本。

页面回退不清除已经形成的合同、归因、佣金、提现和渠道执行事实。

## 附录 B：决策记录

| 决策 | 原因 |
| --- | --- |
| 订单级归因，明细级计佣 | 匹配当前多人购票和按明细退款，支持部分自购排除 |
| 一笔批量订单计一单 | 阶梯奖励成交订单，规则容易解释和审计 |
| 购买意图和订单版本锁定归因 | 对齐当前幂等重试、支付恢复和关闭后重新报名 |
| 独立财务收件箱和账本 | 佣金故障不影响购票出票，支持补账和审计 |
| 用户随时申请，财务批次出款 | 兼顾用户体验、预算、额度和对账 |
| 人工结算先上线 | 无需等待微信商户审核即可形成业务闭环 |
| 微信一位用户一笔单 | 符合新版商家转账确认模式和渠道事实模型 |
| 财务文件必须登录访问 | 结算和税务资料敏感度高于发票短信直达文件 |
| 分销管理使用大会二级模块 | 保持当前后台一级导航稳定 |
| 一级合作伙伴 | 适合当前大会推广场景，合同、归因和风控边界清楚 |
